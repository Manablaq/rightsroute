# RightsRoute architecture specification

## Purpose

RightsRoute is a reusable GenLayer primitive for comparing a structured, declared machine use with a public policy document whose expected raw-byte SHA-256 was registered in advance. It turns that comparison into one bounded, consensus-mediated decision and optional finalized callback.

The architecture deliberately separates source identity and machine-readable decision fields from explanatory text. It does not attempt to create a universal legal conclusion.

## Components

### `RightsRoute`

The primary contract owns policy metadata and assessment state. It registers policy sources, creates use-profile requests, resolves them through `gl.vm.run_nondet_unsafe`, and optionally emits a finalized callback after recording a resolution.

### `RightsRouteCallbackConsumer`

The companion consumer is a minimal reference receiver. Its constructor fixes one permitted RightsRoute sender. It validates callback shape, stores each receipt by assessment ID, accepts exact replays idempotently, and rejects conflicting replays.

## Data model

### Policy lifecycle

```text
ACTIVE → INACTIVE
```

Policies are created by a registrar. Only that registrar may deactivate an active policy. Deactivation prevents new assessment requests but does not alter existing records.

### Assessment lifecycle

```text
REQUESTED → RESOLVED
REQUESTED → CANCELLED
```

`RESOLVED` and `CANCELLED` are terminal. A requester may cancel only its own requested assessment. Any caller may invoke resolution while an assessment is requested.

## Resolution lifecycle

1. A policy is registered with a public HTTPS URI, policy kind, and expected SHA-256.
2. A requester stores an allow-listed use profile and optional callback address. Its canonical JSON is hashed as `use_profile_sha256`.
3. During resolution, the leader fetches the source, limits it to 65,536 bytes, calculates SHA-256 over raw bytes, and requires equality with the registered hash.
4. The source is decoded as UTF-8 and embedded as explicitly untrusted evidence in a fixed prompt.
5. The model must return a JSON decision with allow-listed obligation and restriction codes, evidence items, and a bounded summary.
6. The contract normalizes and rejects malformed, unsupported, duplicated, or contradictory outputs.
7. Validators independently fetch and evaluate the same source. The callback compares source SHA-256, decision, obligations, and restrictions.
8. After `run_nondet_unsafe` returns successfully, the contract stores the result and computes a canonical `resolution_sha256`.
9. If configured, a callback is emitted with `on="finalized"`, so the receiver is notified only after finalization.

## Consensus-critical fields

The validator requires equality for these fields:

- `source_sha256`
- `decision`
- sorted `obligations`
- sorted `restrictions`

Evidence excerpts and the summary are bounded and stored for explanation, but they are not compared as exact prose. This avoids making non-critical wording a consensus dependency while retaining the explanatory record generated by the accepted execution.

## Output vocabulary

Decisions are limited to `PERMITTED`, `PERMITTED_WITH_OBLIGATIONS`, `PROHIBITED`, and `UNDETERMINED`.

The source defines fixed obligation and restriction vocabularies. The contract rejects unsupported codes and invalid combinations such as `PERMITTED` with restrictions or obligations, a prohibited result without a restriction, or an undetermined result that invents a restriction.

## Security boundaries

Policy text is public and untrusted. Prompt-injection defenses, hash-pinning, strict schemas, and validator re-evaluation constrain the workflow, but do not prove that a policy is valid, authoritative, complete, or legally enforceable. See [Security and limits](SECURITY_AND_LIMITS.md).
